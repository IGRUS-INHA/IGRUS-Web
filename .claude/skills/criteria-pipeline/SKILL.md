# 검증 기준 작성-리뷰 파이프라인

criteria-writer 에이전트가 검증 기준을 작성하고, verification-criteria-reviewer 에이전트가 리뷰한 후, 리뷰가 통과되지 않으면 수정-리뷰를 자동으로 반복합니다.

## 사용자 입력

```text
$ARGUMENTS
```

사용자 입력이 비어있으면 AskUserQuestion을 사용하여 검증 기준을 작성할 대상 기능/도메인을 물어보세요.

## 파이프라인 워크플로우

```
사용자 입력 (기능/도메인 설명)
  ↓
Phase 1: 스코프 파악 및 기존 기준 확인
  ↓
Phase 2: criteria-writer 에이전트 실행
  → docs/criteria/ 에 검증 기준 문서 작성
  ↓
Phase 3: 생성된 파일 경로 확인
  ↓
Phase 4: verification-criteria-reviewer 에이전트 실행
  → 리뷰 결과 수신
  ↓
Phase 5: 판정 파싱
  ├── PASS → Phase 7 (완료 보고)
  └── FAIL
       ↓
Phase 6: criteria-writer 재실행 (리뷰 피드백 포함)
  ↓
(Phase 4로 복귀, 최대 3회 반복)
  ↓
Phase 7: 최종 결과 보고
```

## Phase 1: 스코프 파악

1. 사용자 입력에서 대상 기능/도메인을 식별합니다.
2. `Glob`으로 `docs/criteria/**/*.md`를 검색하여 기존 검증 기준 문서를 확인합니다.
3. 관련 기존 문서가 있으면 **업데이트 모드**, 없으면 **신규 작성 모드**로 결정합니다.
4. TodoWrite로 파이프라인 진행 상황을 추적합니다:

```
- [ ] Phase 1: 스코프 파악
- [ ] Phase 2: 검증 기준 초안 작성 (Round 1)
- [ ] Phase 4: 리뷰 (Round 1)
- [ ] Phase 7: 최종 보고
```

## Phase 2: criteria-writer 에이전트 실행

Task 도구로 `criteria-writer` 서브에이전트를 실행합니다.

**프롬프트 구성**:

```
다음 기능에 대한 검증 기준 문서를 작성해주세요.

## 대상 기능
{사용자가 입력한 기능/도메인 설명}

## 모드
{신규 작성 / 업데이트}

## 기존 문서 (업데이트 모드인 경우)
{기존 문서 경로}

## 추가 지시사항
- docs/criteria/ 아래에 저장할 것
- 저장한 파일의 절대 경로를 반드시 출력의 마지막 줄에 명시할 것
  형식: `생성된 파일: {절대 경로}`
```

**수정 모드 프롬프트** (Phase 6에서 재실행 시):

```
다음 검증 기준 문서를 리뷰 피드백에 따라 수정해주세요.

## 대상 문서
{문서 절대 경로}

## 리뷰 피드백
{reviewer가 지적한 이슈 목록 - 🔴 심각 및 🟡 주의}

## 지시사항
- 🔴 심각 이슈를 반드시 모두 해결할 것
- 🟡 주의 이슈도 가능한 한 해결할 것
- 수정 완료 후 파일의 절대 경로를 반드시 출력의 마지막 줄에 명시할 것
  형식: `수정된 파일: {절대 경로}`
```

## Phase 3: 생성 파일 경로 확인

criteria-writer 출력에서 `생성된 파일:` 또는 `수정된 파일:` 패턴으로 파일 경로를 추출합니다.

경로를 찾지 못한 경우:
1. `Glob`으로 `docs/criteria/**/*.md` 최근 수정 파일 탐색
2. 가장 최근에 수정된 파일을 대상 문서로 간주

## Phase 4: verification-criteria-reviewer 에이전트 실행

Task 도구로 `verification-criteria-reviewer` 서브에이전트를 실행합니다.

**프롬프트 구성**:

```
다음 검증 기준 문서를 리뷰해주세요.

## 리뷰 대상
{문서 절대 경로}

## 리뷰 라운드
{현재 라운드 번호} / 3

## 지시사항
- 리뷰 프레임워크의 7가지 관점으로 분석할 것
- 반드시 출력 형식의 📋 판정 섹션을 포함할 것
- 결과는 반드시 **PASS** 또는 **FAIL** 중 하나로 명시할 것
{이전 라운드 피드백이 있으면}
- 이전 라운드에서 지적한 이슈가 해결되었는지 중점적으로 확인할 것
```

## Phase 5: 판정 파싱

reviewer 출력에서 판정 결과를 파싱합니다.

**파싱 규칙**:
1. `결과: **PASS**` 문자열이 포함되어 있으면 → **PASS**
2. `결과: **FAIL**` 문자열이 포함되어 있으면 → **FAIL**
3. 어느 쪽도 명확하지 않으면 → `🔴` 마커가 내용과 함께 있는지 확인하여 판단

**분기 로직**:
- **PASS** → Phase 7 (완료)
- **FAIL** + 현재 라운드 < 3 → Phase 6 (수정)
- **FAIL** + 현재 라운드 >= 3 → Phase 7 (사용자에게 판단 위임)

## Phase 6: criteria-writer 재실행 (수정 모드)

1. reviewer 출력에서 🔴 심각 이슈와 🟡 주의 이슈를 추출합니다.
2. Phase 2의 **수정 모드 프롬프트**를 사용하여 criteria-writer를 재실행합니다.
3. TodoWrite를 업데이트하여 다음 라운드를 추가합니다.
4. Phase 4로 복귀합니다.

## Phase 7: 최종 결과 보고

파이프라인 완료 후 다음 형식으로 최종 결과를 보고합니다:

```markdown
---

## 검증 기준 파이프라인 완료

| 항목 | 결과 |
|------|------|
| 대상 기능 | {기능명} |
| 생성된 문서 | `{파일 경로}` |
| 리뷰 라운드 | {총 라운드 수}회 |
| 최종 판정 | {PASS / FAIL (사용자 판단 필요)} |

### 리뷰 이력
| 라운드 | 판정 | 주요 이슈 |
|--------|------|----------|
| 1 | {PASS/FAIL} | {주요 이슈 요약} |
| 2 | {PASS/FAIL} | {주요 이슈 요약} |
| ... | ... | ... |

---
```

**FAIL로 종료된 경우** 추가 안내:
```markdown
### 사용자 판단 필요

3회 반복 후에도 다음 이슈가 해결되지 않았습니다:
{미해결 🔴 이슈 목록}

다음 중 하나를 선택해주세요:
1. 현재 상태로 문서를 수락
2. 수동으로 추가 수정
3. 파이프라인을 다시 실행
```

## 주의사항

- 각 에이전트 실행 시 `Task` 도구의 `subagent_type` 파라미터를 정확히 지정할 것
  - 작성: `subagent_type: "criteria-writer"`
  - 리뷰: `subagent_type: "verification-criteria-reviewer"`
- 에이전트 실행 결과를 파싱할 때, 결과 텍스트 전체를 다음 에이전트에 전달하지 말고 핵심 정보만 추출하여 전달할 것
- 파이프라인 중간에 에이전트 실행이 실패하면, 에러 내용을 사용자에게 보고하고 중단할 것
- `docs/criteria/` 디렉토리가 존재하지 않으면 criteria-writer가 자동으로 생성함
