# 코드 구현-리뷰 파이프라인

검증 기준, 테스트 케이스, 작업 계획 문서를 기반으로 code-implementer 에이전트가 코드를 구현하고, spec-reviewer와 code-reviewer 에이전트가 병렬로 리뷰합니다. 리뷰를 통과하지 못하면 수정-리뷰를 자동으로 반복합니다.

## 사용자 입력

```text
$ARGUMENTS
```

사용자 입력이 비어있으면 AskUserQuestion을 사용하여 다음을 질문하세요:
1. 구현할 기능/도메인이 무엇인가요?
2. 검증 기준 문서 경로는 어디인가요?
3. 테스트 케이스 문서 경로는 어디인가요?
4. 작업 계획 문서 경로는 어디인가요?

## 파이프라인 워크플로우

```
사용자 입력 (기능명 + 문서 경로)
  ↓
Phase 1: 입력 확인 및 문서 검증
  ↓
Phase 2: 작업 계획 파싱 및 그룹 분할
  ↓
Phase 3: 공유 체크리스트 생성
  ↓
Phase 4: 작업 그룹별 구현-리뷰 루프 ←──────────────────┐
  │                                                      │
  Phase 4a: code-implementer 실행 (구현)                  │
  Phase 4b: 구현 결과 확인                                │
  Phase 4c: spec-reviewer + code-reviewer 병렬 실행       │
  Phase 4d: 양쪽 판정 파싱 및 통합                        │
    ├── 양쪽 PASS → 다음 그룹                             │
    └── 하나 이상 FAIL → Phase 4e (수정)                  │
  Phase 4e: 피드백 통합 → code-implementer 재실행 ───────┘
       (최대 3회 반복)
  ↓
Phase 5: 전체 테스트 실행
  ↓
Phase 6: 체크리스트 최종 업데이트
  ↓
Phase 7: 최종 결과 보고
```

## Phase 1: 입력 확인 및 문서 검증

1. 사용자 입력에서 다음 정보를 추출합니다:
   - 대상 기능/도메인명
   - 검증 기준 문서 경로
   - 테스트 케이스 문서 경로
   - 작업 계획 문서 경로
2. 누락된 정보가 있으면 AskUserQuestion으로 질문합니다.
3. 제공된 문서 경로가 실제로 존재하는지 `Read`로 확인합니다. 파일이 없으면 사용자에게 경로를 다시 물어봅니다.
4. TodoWrite로 파이프라인 진행 상황을 추적합니다:

```
- [ ] Phase 1: 입력 확인
- [ ] Phase 2: 작업 그룹 분할
- [ ] Phase 3: 체크리스트 생성
- [ ] Phase 4: 그룹별 구현-리뷰
- [ ] Phase 5: 전체 테스트
- [ ] Phase 7: 최종 보고
```

## Phase 2: 작업 계획 파싱 및 그룹 분할

작업 계획 문서를 읽고 TASK 목록을 파싱하여 그룹으로 분할합니다.

### 파싱 대상

작업 계획 문서에서 다음을 추출합니다:
- **TASK-ID**: `TASK-NNN` 형식
- **작업명**: 각 TASK의 제목
- **선행 작업**: 의존성 정보
- **관련 검증 기준**: `STOR-INV-XX`, `SEC-XX` 등
- **관련 테스트 케이스**: `TC-XXX`
- **구현 범위**: backend / frontend / both
- **예상 난이도**: 상 / 중 / 하
- **권장 실행 순서**: Phase별 구조

### 그룹 분할 알고리즘

1. 작업 계획의 **"권장 실행 순서"** Phase 구조를 기본 그룹으로 사용합니다.
2. 각 그룹이 **5~7개 TASK**를 초과하면, 의존성을 존중하며 서브그룹으로 분할합니다.
3. 가능하면 **구현 TASK와 대응 테스트 TASK**를 같은 그룹에 배치합니다.
4. **선행 작업이 다른 그룹에 있는 TASK**는 반드시 해당 그룹 이후에 배치합니다.
5. "선택" 또는 "선택사항"으로 표시된 TASK는 별도 그룹으로 분리합니다.

### 사용자 확인

그룹 분할 결과를 AskUserQuestion으로 사용자에게 제시하여 확인을 받습니다:

```markdown
## 작업 그룹 분할안

### 그룹 1: {Phase명} ({N}개 작업)
- TASK-001: {작업명}
- TASK-002: {작업명}
- ...

### 그룹 2: {Phase명} ({N}개 작업)
- TASK-004: {작업명}
- ...

{선택적 그룹이 있으면}
### 그룹 N: (선택사항)
- TASK-027: {작업명}

이 분할로 진행할까요? 조정이 필요하면 말씀해주세요.
```

## Phase 3: 공유 체크리스트 생성

작업 계획과 같은 하위 디렉토리에 체크리스트 파일을 생성합니다.

**파일 위치**: 작업 계획 문서와 같은 디렉토리 (예: `docs/feature/storage/implementation-checklist.md`)

**기존 체크리스트 확인**: 해당 경로에 이미 체크리스트가 존재하면 AskUserQuestion으로 사용자에게 질문합니다:
- "이전 체크리스트가 존재합니다. 이어서 진행할까요? (미완료 그룹 {N}부터)"
- 이어서 진행하면 기존 체크리스트를 읽고 미완료 그룹부터 Phase 4를 시작합니다.
- 새로 시작하면 기존 체크리스트를 덮어씁니다.

**체크리스트 형식**:

```markdown
# {기능명} 구현 체크리스트

## 메타데이터
| 항목 | 값 |
|------|---|
| 생성일 | {YYYY-MM-DD} |
| 최종 업데이트 | {YYYY-MM-DD HH:MM} |
| 검증 기준 문서 | `{절대 경로}` |
| 테스트 케이스 문서 | `{절대 경로}` |
| 작업 계획 문서 | `{절대 경로}` |
| 전체 상태 | IN_PROGRESS |

## 작업 진행 현황

### 그룹 1: {그룹 설명}
| TASK-ID | 작업명 | 구현 상태 | 리뷰 상태 | 파일 | 비고 |
|---------|--------|----------|----------|------|------|
| TASK-001 | {작업명} | PENDING | - | - | - |
| TASK-002 | {작업명} | PENDING | - | - | - |

**그룹 상태**: PENDING
**리뷰 이력**: -

---

### 그룹 2: {그룹 설명}
| TASK-ID | 작업명 | 구현 상태 | 리뷰 상태 | 파일 | 비고 |
|---------|--------|----------|----------|------|------|
| ... | ... | PENDING | - | - | - |

**그룹 상태**: PENDING
**리뷰 이력**: -

---

## 검증 기준 충족 현황
| ID | 설명 | 관련 TASK | 상태 |
|----|------|----------|:----:|
| {INV-ID} | {설명} | {TASK-IDs} | ⬜ |

## 테스트 케이스 통과 현황
| TC-ID | 설명 | 관련 TASK | 상태 |
|-------|------|----------|:----:|
| {TC-ID} | {설명} | {TASK-IDs} | ⬜ |

## 이슈 로그
| # | 라운드 | 그룹 | 심각도 | 리뷰어 | 설명 | 해결 |
|---|--------|------|--------|--------|------|------|
```

`Write` 도구로 체크리스트 파일을 생성합니다.

## Phase 4: 작업 그룹별 구현-리뷰 루프

각 그룹에 대해 다음 서브페이즈를 실행합니다. 한 그룹이 완료(PASS)되어야 다음 그룹으로 진행합니다.

### Phase 4a: code-implementer 에이전트 실행

Task 도구로 `code-implementer` 서브에이전트를 실행합니다.

**신규 구현 모드 프롬프트**:

```
다음 작업 그룹을 구현해주세요.

## 작업 그룹 ({N} / {총 그룹 수})
{TASK-ID별 작업명과 요약 목록}

## 입력 문서
- 검증 기준 문서: {절대 경로}
- 테스트 케이스 문서: {절대 경로}
- 작업 계획 문서: {절대 경로}

## 공유 체크리스트
{체크리스트 절대 경로}

## 지시사항
- 각 TASK의 구현 범위와 관련 검증 기준/테스트 케이스를 확인할 것
- 프로젝트 CLAUDE.md 규칙을 준수할 것
- 구현 완료 후 체크리스트를 업데이트할 것
- 생성/수정된 파일 경로를 반드시 보고할 것
  형식: `생성된 파일: {절대 경로}` 또는 `수정된 파일: {절대 경로}`
```

**수정 모드 프롬프트** (Phase 4e에서 재실행 시):

```
다음 리뷰 피드백에 따라 코드를 수정해주세요.

## 작업 그룹 ({N} / {총 그룹 수})
{TASK-ID별 작업명 목록}

## 리뷰 피드백

### 명세 검증 피드백 (spec-reviewer)
{spec-reviewer가 FAIL인 경우: 🔴 필수 수정 사항 + 🟡 권장 수정 사항}
{spec-reviewer가 PASS인 경우: 🟡 권장 수정 사항만 (참고용, 선택적)}
(spec-reviewer가 PASS이고 🟡도 없는 경우 이 섹션 생략)

### 코드 리뷰 피드백 (code-reviewer)
{code-reviewer가 FAIL인 경우: 🔴 필수 수정 사항 + 🟡 권장 수정 사항}
{code-reviewer가 PASS인 경우: 🟡 권장 수정 사항만 (참고용, 선택적)}
(code-reviewer가 PASS이고 🟡도 없는 경우 이 섹션 생략)

## 참조 문서
- 검증 기준: {절대 경로}
- 테스트 케이스: {절대 경로}
- 작업 계획: {절대 경로}

## 공유 체크리스트
{체크리스트 절대 경로}

## 지시사항
- 🔴 필수 수정 사항을 반드시 모두 해결할 것
- 🟡 권장 수정 사항도 가능한 한 해결할 것
- 수정 완료 후 체크리스트를 업데이트할 것
- 수정된 파일 경로를 반드시 보고할 것
  형식: `수정된 파일: {절대 경로}`
```

### Phase 4b: 구현 결과 확인

code-implementer 출력에서 `생성된 파일:` 또는 `수정된 파일:` 패턴으로 파일 경로를 추출합니다.

경로를 찾지 못한 경우:
1. `Glob`으로 `backend/src/**/*.java` 및 `frontend/src/**/*.ts{,x}` 최근 수정 파일 탐색
2. `git diff --name-only HEAD` (Bash)로 변경 파일 확인

체크리스트 파일을 `Read`로 읽어 업데이트 상태를 확인합니다.

### Phase 4c: spec-reviewer + code-reviewer 병렬 실행

**spec-reviewer와 code-reviewer를 동시에 실행합니다.** 두 리뷰어는 모두 읽기 전용이므로 병렬 실행 시 충돌이 없습니다.

하나의 메시지에서 두 개의 Task 도구 호출을 병렬로 실행합니다:

**Task 1: spec-reviewer 프롬프트**:

```
다음 코드 구현을 검증 기준/테스트 케이스 문서 대비 검증해주세요.

## 리뷰 대상
- 작업 그룹: {TASK-ID 목록}
- 구현된 파일: {파일 경로 목록}

## 참조 문서
- 검증 기준: {절대 경로}
- 테스트 케이스: {절대 경로}
- 작업 계획: {절대 경로}

## 공유 체크리스트
{체크리스트 절대 경로}

## 리뷰 라운드
{현재 라운드} / 3

## 지시사항
- 5가지 관점(검증 기준 충족, TC 충족, 작업 계획 완전성, 체크리스트 정합성, 엣지 케이스)으로 분석할 것
- 반드시 📋 판정 섹션을 포함할 것
- 결과는 반드시 **PASS** 또는 **FAIL** 중 하나로 명시할 것
{이전 라운드 피드백이 있으면}
- 이전 라운드에서 지적한 이슈가 해결되었는지 중점적으로 확인할 것
```

**Task 2: code-reviewer 프롬프트**:

```
다음 코드 구현을 코드 품질/보안/규칙 준수 관점에서 리뷰해주세요.

## 리뷰 대상
- 작업 그룹: {TASK-ID 목록}
- 구현된 파일: {파일 경로 목록}

## 공유 체크리스트
{체크리스트 절대 경로}

## 리뷰 라운드
{현재 라운드} / 3

## 지시사항
- 6가지 관점(규칙 준수, 버그, 보안, 트랜잭션/JPA, 에러 처리, 코드 품질)으로 분석할 것
- 반드시 📋 판정 섹션을 포함할 것
- 결과는 반드시 **PASS** 또는 **FAIL** 중 하나로 명시할 것
{이전 라운드 피드백이 있으면}
- 이전 라운드에서 지적한 이슈가 해결되었는지 중점적으로 확인할 것
```

### Phase 4d: 양쪽 판정 파싱 및 통합

양쪽 리뷰 결과를 각각 파싱합니다.

**파싱 규칙** (각 리뷰어에 대해):
1. `결과: **PASS**` 문자열이 포함되어 있으면 → **PASS**
2. `결과: **FAIL**` 문자열이 포함되어 있으면 → **FAIL**
3. 어느 쪽도 명확하지 않으면 → `🔴` 마커가 내용과 함께 있는지 확인하여 판단

**통합 분기 로직**:
- spec-reviewer **PASS** + code-reviewer **PASS** → 체크리스트 업데이트 (그룹 상태: PASS, 검증 기준/TC 상태 업데이트) → 다음 그룹으로
- 하나 이상 **FAIL** + 현재 라운드 < 3 → Phase 4e (수정)
- 하나 이상 **FAIL** + 현재 라운드 >= 3 → Phase 7 방향으로 사용자에게 판단 위임

### Phase 4e: 피드백 통합 및 재실행

1. 양쪽 리뷰어의 출력에서 🔴 필수 수정 사항과 🟡 권장 수정 사항을 추출합니다.
2. FAIL한 리뷰어의 피드백은 전부 포함하고, PASS한 리뷰어의 🟡 권장 사항은 참고용으로 포함합니다.
3. 체크리스트의 이슈 로그에 추가합니다 (Edit 도구 사용).
4. Phase 4a의 **수정 모드 프롬프트**를 사용하여 code-implementer를 재실행합니다.
5. TodoWrite를 업데이트하여 다음 라운드를 표시합니다.
6. Phase 4c로 복귀합니다 (다시 양쪽 병렬 리뷰).

### 그룹 PASS 시 체크리스트 업데이트

그룹이 PASS하면 `Edit` 도구로 체크리스트를 업데이트합니다:

1. **그룹 상태** → `PASS`
2. **리뷰 이력** → 라운드별 결과 기록
3. **검증 기준 충족 현황** → 해당 그룹의 검증 기준 항목을 `⬜` → `✅`로 업데이트
4. **테스트 케이스 통과 현황** → 해당 그룹의 TC 항목을 `⬜` → `✅`로 업데이트

## Phase 5: 전체 테스트 실행

모든 그룹이 완료된 후, 전체 테스트를 실행합니다:

**Backend**:
```bash
cd /c/dev/IGRUS-Web/backend && ./gradlew test
```

**Frontend** (프론트엔드 TASK가 있는 경우):
```bash
cd /c/dev/IGRUS-Web/frontend && npm test
```

테스트 실패 시:
1. 실패한 테스트를 분석하여 관련 그룹을 식별합니다.
2. 해당 그룹에 대해 Phase 4e (수정 루프)를 다시 실행합니다.
3. 수정 후 다시 전체 테스트를 실행합니다.

## Phase 6: 체크리스트 최종 업데이트

`Edit` 도구로 체크리스트의 메타데이터를 업데이트합니다:
- **최종 업데이트** 시간 갱신
- **전체 상태** → `COMPLETED` (모든 그룹 PASS) 또는 `PARTIAL` (일부 그룹 미완료)
- 이슈 로그의 모든 항목에 최종 해결 상태 기록

## Phase 7: 최종 결과 보고

파이프라인 완료 후 다음 형식으로 최종 결과를 보고합니다:

```markdown
---

## 구현 파이프라인 완료 보고

| 항목 | 결과 |
|------|------|
| 대상 기능 | {기능명} |
| 작업 그룹 수 | {N}개 |
| 총 작업 수 / 완료 | {N} / {N} |
| 총 리뷰 라운드 | {N}회 |
| 최종 테스트 | {PASS / FAIL} |
| 체크리스트 | `{체크리스트 경로}` |

### 그룹별 결과
| 그룹 | TASK-IDs | 명세 검증 | 코드 리뷰 | 라운드 | 최종 |
|------|----------|----------|----------|--------|------|
| 1 | TASK-001~007 | PASS | PASS | 1 | PASS |
| 2 | TASK-004,006,014 | PASS | PASS | 2 | PASS |
| ... | ... | ... | ... | ... | ... |

### 검증 기준 충족 최종 현황
| ID | 충족 |
|----|:----:|
| {INV-ID} | ✅ / ❌ |

### 테스트 케이스 통과 최종 현황
| TC-ID | 통과 |
|-------|:----:|
| {TC-ID} | ✅ / ❌ |

---
```

**FAIL로 종료된 그룹이 있는 경우** 추가 안내:
```markdown
### 사용자 판단 필요

다음 그룹이 3회 반복 후에도 PASS하지 못했습니다:
- 그룹 {N}: {미해결 🔴 이슈 요약}

다음 중 하나를 선택해주세요:
1. 현재 상태로 수락
2. 수동으로 추가 수정
3. 해당 그룹만 파이프라인 재실행
```

## 주의사항

- 각 에이전트 실행 시 `Task` 도구의 `subagent_type` 파라미터를 정확히 지정할 것:
  - 구현: `subagent_type: "code-implementer"`
  - 명세 검증: `subagent_type: "spec-reviewer"`
  - 코드 리뷰: `subagent_type: "code-reviewer"`
- 에이전트 실행 결과를 파싱할 때, 결과 텍스트 전체를 다음 에이전트에 전달하지 말고 핵심 정보만 추출하여 전달할 것
- 파이프라인 중간에 에이전트 실행이 실패하면, 에러 내용을 사용자에게 보고하고 중단할 것
- 3개 문서 경로는 모든 라운드에서 일관되게 유지할 것
- spec-reviewer와 code-reviewer를 하나의 메시지에서 동시에 Task 도구를 호출하여 병렬 실행할 것
- 양쪽 리뷰 결과를 통합하여 판정할 것: 양쪽 PASS → 그룹 PASS, 하나 이상 FAIL → 피드백 합쳐서 수정 루프
- 체크리스트 파일은 파이프라인과 code-implementer만 수정하고, 리뷰어들은 읽기만 할 것
- 그룹 분할 결과는 반드시 사용자 확인을 받을 것
