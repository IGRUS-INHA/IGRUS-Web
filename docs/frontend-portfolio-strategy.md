# 프론트엔드 취업 준비 전략

IGRUS-Web 프로젝트를 활용한 프론트엔드 개발자 포트폴리오 강화 전략.

## 현재 프로젝트 상태 분석

### 이미 갖춰진 강점

| 항목 | 설명 |
|------|------|
| Contract-First API | OpenAPI 스펙 + Orval 자동 생성 |
| 엄격한 TypeScript | `any`, `as`, `!` 금지 |
| 인증 시스템 | Access/Refresh 토큰, pre-emptive 갱신, 탈취 감지 |
| Role-based 라우팅 | 4단계 권한 (ASSOCIATE → ADMIN) |
| 에러 처리 체계 | 148개 에러 코드 매핑, ApiError 클래스 |
| 디자인 토큰 | Tailwind 기반 커스텀 테마 (색상, 간격, 라디우스) |

### 부족한 영역 (개선 기회)

| 항목 | 현재 상태 |
|------|----------|
| 성능 최적화 | 코드 스플리팅, lazy loading 없음 |
| 접근성 | 기본 ARIA만 적용, 체계적 WCAG 미준수 |
| 테스트 | 프론트엔드 테스트 0개 |
| 모니터링 | 에러 로깅, 분석 도구 없음 |
| Error Boundary | 미적용 |
| CI/CD 품질 게이트 | 프론트엔드 전용 파이프라인 없음 |
| 다크모드 | 토글만 존재, 미완성 |

## 작업 우선순위

포트폴리오 임팩트 순서로 정렬. 각 작업은 "문제 인식 → 측정 → 해결 → 결과" 구조로 서술 가능해야 한다.

### 1순위: 성능 최적화 + 수치 증명

**포트폴리오 임팩트: 매우 높음 | 난이도: 중 | 소요: 1~2주**

대부분의 주니어 포트폴리오에 없고, 숫자로 바로 증명할 수 있다.

#### 할 일

- [ ] Lighthouse로 현재 성능 점수 스크린샷 (기준선 확보)
- [ ] Route 기반 코드 스플리팅 (`React.lazy` + `Suspense`)
- [ ] `vite-bundle-visualizer`로 번들 분석
- [ ] 이미지 최적화 (WebP 변환, lazy loading)
- [ ] `web-vitals` 라이브러리 연동
- [ ] 개선 후 Lighthouse 재측정 및 before/after 기록

#### 측정 지표

| 지표 | 측정 방법 | 좋음 기준 |
|------|----------|----------|
| LCP (Largest Contentful Paint) | Lighthouse / web-vitals | < 2.5s |
| INP (Interaction to Next Paint) | Lighthouse / web-vitals | < 200ms |
| CLS (Cumulative Layout Shift) | Lighthouse / web-vitals | < 0.1 |
| 초기 번들 사이즈 | vite-bundle-visualizer | 최소화 |

#### 포트폴리오 서술 예시

> 32개 페이지가 단일 번들로 로드되고 있었음. Route 기반 코드 스플리팅 적용으로 초기 번들 사이즈 850KB → 320KB (62% 감소), LCP 3.1s → 1.6s 개선.

## 사용성 개선 수치화 방법

### 변인 통제 문제

사용성 지표 개선이 "내가 한 작업 때문"인지 확신하기 어렵다. 다음 변인들이 혼입될 수 있다.

| 혼입 변인 | 예시 |
|-----------|------|
| 시기 효과 | 학기 초 가입 폭증, 시험 기간 이탈 |
| 콘텐츠 효과 | 매력적인 이벤트가 올라와서 체류시간 증가 |
| 사용자 구성 변화 | 신입 부원 유입으로 행동 패턴 자체가 다름 |
| 동시 변경 | UI 개선 + API 속도 개선 동시 배포 |
| 학습 효과 | 사용자가 사이트에 익숙해져서 자연 개선 |

### A/B 테스트 현실

통계적 유의성을 확보하려면 상당한 트래픽이 필요하다.

```
필요 샘플 크기 ≈ 16 × p(1-p) / δ²
(α=0.05, 검정력=80% 기준)
```

| 기존 전환율 | 개선폭 5%p | 개선폭 10%p | 개선폭 15%p |
|------------|-----------|------------|------------|
| 10% | 576명 | 144명 | 64명 |
| 30% | 1,344명 | 336명 | 149명 |
| 50% | 1,600명 | 400명 | 178명 |

동아리 웹(추정 MAU 200~400)에서는 큰 개선(15%p+)만 감지 가능하고, 작은 개선(5%p 이하)은 사실상 불가능하다.

### 현실적 대안

A/B 테스트 대신 다음 방법을 조합한다.

1. **전후 비교**: 변경 전 2주, 변경 후 2주 동일 지표 비교. 한 번에 하나만 변경.
2. **세그먼트 분석**: 기존 부원 vs 신규 부원, 모바일 vs 데스크톱으로 쪼개서 분석.
3. **직접 지표 사용**: "월간 활성 사용자" 같은 모호한 지표 대신, "폼 입력 에러율", "작업 완료 시간" 같은 변경과 직접 연결된 지표 사용.
4. **Lighthouse 점수**: 성능/접근성은 도구가 자동 측정하므로 변인 통제 문제 자체가 없음. 포트폴리오에 가장 적합.

## 포트폴리오 서술 원칙

### 구조

모든 작업을 다음 4단계로 서술한다.

```
1. 문제 인식: 무엇이 문제였는가
2. 측정: 현재 상태를 수치로 파악
3. 해결: 어떤 기술/방법으로 해결했는가
4. 결과: 개선된 수치, 검증 방법
```

### 좋은 예 vs 나쁜 예

```
나쁜 예:
"React + TypeScript로 동아리 웹사이트를 만들었습니다."
"Lighthouse 점수 95점입니다."
"반응형 디자인을 적용했습니다."

좋은 예:
"32개 페이지가 단일 번들로 로드되는 성능 문제를 발견.
 Route 기반 코드 스플리팅으로 초기 번들 62% 감소, LCP 48% 개선."

"Lighthouse 접근성 감사 결과 67점.
 포커스 관리, 컬러 대비, 키보드 접근성 총 17건 수정 후 96점 달성."

"프로덕션 에러 추적 부재로 사용자 영향 파악 불가.
 3단계 Error Boundary + Sentry 연동으로 에러 감지 시간 < 1분 달성."
```

## 면접 스토리텔링 (STAR 원칙)

기술 면접에서 프로젝트 경험을 설명할 때 STAR 구조를 활용한다.

### 예시 1: 성능 최적화 — 코드 스플리팅과 번들 분석

```
[Situation] 동아리 웹사이트에 32개 페이지가 있는데, 모든 페이지가 하나의 번들로
            빌드되어 초기 로딩이 느리고 Lighthouse 성능 점수가 낮은 상태

[Task]      초기 로딩 성능을 개선하고, 이를 수치로 증명할 수 있는 측정 체계를 구축

[Action]    - vite-bundle-visualizer로 번들 구성을 분석하여 병목 지점 식별
            - React.lazy + Suspense로 Route 기반 코드 스플리팅 적용
            - 에디터(Novel/Tiptap) 등 무거운 라이브러리를 동적 임포트로 분리
            - 이미지에 lazy loading 적용, WebP 포맷 전환
            - web-vitals 라이브러리를 연동하여 실 사용자 성능 데이터 수집 시작

[Result]    - 초기 번들 사이즈 850KB → 320KB (62% 감소)
            - LCP 3.1s → 1.6s (48% 개선), Lighthouse 성능 점수 58 → 91
            - web-vitals 연동으로 배포 후에도 성능 리그레션을 지속 모니터링
```

### 예시 2: 접근성 체계적 개선

```
[Situation] 기본적인 ARIA 속성만 적용된 상태에서 Lighthouse 접근성 감사를 실행했더니
            67점으로, WCAG AA 기준에 미달하는 항목이 다수 발견됨

[Task]      접근성 점수를 95점 이상으로 올리고,
            스크린 리더 사용자도 핵심 플로우를 완료할 수 있도록 개선

[Action]    - eslint-plugin-jsx-a11y를 도입하여 빌드 타임에 접근성 위반 자동 감지
            - skip-to-content 링크 추가로 키보드 사용자의 반복 탐색 제거
            - 모달, 사이드바에 focus trap 구현 (열릴 때 포커스 이동, 닫힐 때 원래 위치 복귀)
            - 전체 페이지 키보드 네비게이션 점검, Tab 순서가 논리적이지 않은 17곳 수정
            - 컬러 대비 비율 검사 후 WCAG AA 기준(4.5:1) 미달 색상 5건 수정
            - NVDA 스크린 리더로 로그인 → 글 작성 → 이벤트 신청 플로우 전체 테스트

[Result]    - Lighthouse 접근성 점수 67 → 96
            - eslint-plugin-jsx-a11y 위반 0건 유지
            - 스크린 리더로 핵심 플로우 3개 완료 검증
```

### 예시 3: Error Boundary 계층 설계 + 모니터링

```
[Situation] React 앱에 Error Boundary가 없어서, 컴포넌트 렌더링 에러 발생 시
            전체 화면이 흰 화면(white screen)이 되는 상황.
            에러가 발생해도 추적할 수 있는 수단이 없어 사용자 영향을 파악할 수 없었음

[Task]      사용자가 에러를 만나도 앱을 계속 사용할 수 있도록 복원력을 확보하고,
            발생한 에러를 자동으로 수집/추적하는 인프라를 구축

[Action]    - 3단계 Error Boundary 전략 설계:
              App 레벨 (치명적 에러 → 전체 fallback),
              Page 레벨 (페이지 에러 → 해당 페이지만 fallback + 재시도 버튼),
              Widget 레벨 (댓글, 사이드바 등 → 해당 영역만 fallback)
            - 각 레벨별 사용자 친화적 fallback UI 구현 (에러 메시지 + 복구 액션)
            - Sentry 연동으로 에러 자동 수집, 소스맵 업로드로 스택 트레이스 가독성 확보
            - Slack 알림 파이프라인 구성으로 에러 발생 즉시 팀에 전파

[Result]    - 흰 화면 발생 가능 지점 0개 (모든 페이지 Error Boundary 커버)
            - 에러 발생 시 평균 감지 시간 < 1분 (Sentry + Slack 알림)
            - 사용자는 에러가 난 영역 외의 기능을 계속 사용 가능
```

### 예시 4: 프론트엔드 테스트 전략 수립

```
[Situation] 프론트엔드 테스트가 0개인 상태. 백엔드는 1,300+ 테스트가 있지만,
            프론트엔드는 UI 변경이나 리팩토링 시 수동으로 전체 플로우를 확인해야 했음

[Task]      핵심 사용자 플로우를 자동으로 검증할 수 있는 테스트 체계를 처음부터 구축

[Action]    - Vitest + Testing Library 환경 구성 (Vite 네이티브 테스트 러너 활용)
            - MSW(Mock Service Worker)로 API 레이어를 격리하여
              백엔드 없이도 프론트엔드 테스트가 독립적으로 실행 가능하도록 설계
            - 테스트 대상 우선순위: 인증 플로우 > 게시글 CRUD > 이벤트 신청 > 관리자
            - 컴포넌트 단위 테스트: Button, Input, Toast 등 공통 UI의 렌더링/인터랙션 검증
            - 통합 테스트: 로그인 → 토큰 저장 → 인증된 API 호출까지 전체 플로우 검증
            - CI(GitHub Actions)에서 매 PR마다 테스트 자동 실행

[Result]    - 유닛 테스트 42개 + 통합 테스트 16개 작성
            - MSW로 OpenAPI 스펙 기반 mock handler를 생성하여 API 변경에도 자동 대응
            - PR 머지 전 자동 검증으로 UI 리그레션 사전 차단
```

### 예시 5: 사용자 분석 인프라 구축 + 데이터 기반 개선

```
[Situation] 웹사이트에 분석 도구가 전혀 없어서, 어떤 페이지가 많이 사용되는지,
            사용자가 어디서 이탈하는지 전혀 파악할 수 없는 상태

[Task]      사용자 행동 데이터를 수집하는 인프라를 구축하고,
            데이터 기반으로 실제 UX 개선 제안을 도출

[Action]    - PostHog(오픈소스) 연동, 개인정보 보호를 위해 IP 익명화 설정
            - 핵심 이벤트 정의: 페이지뷰, 버튼 클릭, 폼 제출, 에러 발생
            - 퍼널 5개 설계: 회원가입, 로그인, 글 작성, 이벤트 신청, 문의 제출
            - 세그먼트 분석 기준 설정: 기존 부원 vs 신규 부원, 모바일 vs 데스크톱
            - 2주간 데이터 수집 후 분석 실시

[Result]    - 이벤트 신청 퍼널에서 상세페이지 → 신청 단계 이탈률 40% 발견
            - 원인 분석: 신청 버튼이 스크롤 아래에 위치, 모바일에서 특히 심각
            - CTA 버튼 위치 변경 + 신청 폼 간소화를 데이터 근거와 함께 제안
```

## 기술 면접 예상 질문

### 성능

| 예상 질문 | 답변 핵심 |
|----------|----------|
| 코드 스플리팅이란? | 하나의 큰 번들을 여러 청크로 분리하여 필요한 시점에 로드. React.lazy + Suspense로 Route 단위 적용 |
| LCP를 개선하려면? | 초기 번들 축소(코드 스플리팅), 이미지 최적화(WebP, lazy loading), 크리티컬 CSS 인라인, 서버 응답 시간 단축 |
| CLS가 발생하는 원인은? | 이미지/광고의 크기 미지정, 동적 콘텐츠 삽입, 웹폰트 로드 시 레이아웃 변경(FOUT) |
| Tree Shaking이란? | 번들러가 사용되지 않는 코드를 제거하는 최적화. ESM의 정적 분석이 가능한 특성을 활용 |
| web-vitals를 왜 사용하나? | Lighthouse는 실험실 환경 측정이고, web-vitals는 실 사용자 환경(RUM) 데이터. 둘 다 필요 |

### 접근성

| 예상 질문 | 답변 핵심 |
|----------|----------|
| WCAG AA와 AAA 차이? | AA는 최소 권장 기준(대비 4.5:1), AAA는 강화 기준(대비 7:1). 실무에서는 AA 준수가 일반적 |
| focus trap이 필요한 이유? | 모달 열린 상태에서 Tab이 모달 밖으로 나가면 스크린 리더 사용자가 컨텍스트를 잃음 |
| skip-to-content란? | 키보드 사용자가 매번 헤더/네비게이션을 탭하지 않고 본문으로 바로 이동할 수 있는 링크 |
| aria-live의 용도? | 동적으로 변하는 콘텐츠(토스트, 알림)를 스크린 리더에게 자동으로 알리는 속성 |

### 에러 처리

| 예상 질문 | 답변 핵심 |
|----------|----------|
| Error Boundary의 한계? | 이벤트 핸들러, 비동기 코드, SSR에서는 잡지 못함. try-catch와 병행 필요 |
| Error Boundary를 왜 계층화? | 에러 범위를 최소화하기 위해. 댓글 에러로 전체 페이지가 죽으면 안 됨 |
| Sentry 소스맵은 왜 필요? | 프로덕션 코드는 minify되어 스택 트레이스가 읽기 불가. 소스맵이 있어야 원본 코드 위치 추적 가능 |

### 테스트

| 예상 질문 | 답변 핵심 |
|----------|----------|
| MSW를 왜 사용? | 실제 네트워크를 가로채서 모킹하므로 fetch/axios 등 구현에 무관하게 동작. 테스트와 개발 서버 모두에서 사용 가능 |
| 컴포넌트 테스트 vs E2E 차이? | 컴포넌트 테스트는 단위 격리, 빠르고 안정적. E2E는 브라우저 전체 동작 검증, 느리지만 현실적 |
| 무엇을 테스트해야 하나? | 사용자 행동 기준으로 테스트. 구현 세부사항(state, 내부 함수)이 아니라 "사용자가 보는 결과"를 검증 |
| 테스트 커버리지 100%가 필요한가? | 불필요. 핵심 비즈니스 플로우 80%+ 커버가 더 효율적. 커버리지 숫자보다 테스트 품질이 중요 |

### 설계/아키텍처

| 예상 질문 | 답변 핵심 |
|----------|----------|
| Zustand를 Redux 대신 선택한 이유? | 보일러플레이트 최소화, 번들 사이즈 작음(~1KB), React 외부에서도 사용 가능. 이 프로젝트 규모에서 Redux는 과도 |
| TanStack Query의 staleTime이란? | 데이터가 "신선"한 것으로 간주하는 시간. 이 시간 내에는 refetch하지 않아 불필요한 네트워크 요청 방지 |
| Orval을 사용하는 이유? | OpenAPI 스펙에서 TypeScript 타입 + TanStack Query 훅을 자동 생성. API 변경 시 타입 불일치를 컴파일 타임에 감지 |
| Feature Flag를 왜 사용? | 코드를 배포하되 기능을 비활성화할 수 있어서, 불완전한 기능도 main에 머지 가능. 점진적 롤아웃에 활용 |

## CS 기본기와 연결짓기

프로젝트 구현을 CS 기본 개념과 연결하면 면접에서 깊이가 더해진다.

| CS 개념 | 프로젝트 연결 |
|---------|-------------|
| 네트워크 (HTTP 캐싱) | staleTime, Cache-Control 헤더, 조건부 요청(ETag) |
| 자료구조 (트리) | React 컴포넌트 트리, Error Boundary의 에러 전파 (가장 가까운 Boundary에서 catch) |
| 운영체제 (메모리) | 번들 사이즈 = 브라우저 메모리 부담, 코드 스플리팅 = 지연 로딩(demand paging과 유사) |
| 보안 | XSS 방지, CSRF(SameSite 쿠키), 토큰 저장 위치(localStorage vs HttpOnly Cookie) |
| 소프트웨어 공학 | 컴포넌트 = SRP, Compound Component = OCP, 디자인 토큰 = DRY |
| 데이터베이스 | 클라이언트 캐시(TanStack Query) = 읽기 캐시, optimistic update = 낙관적 잠금의 프론트 버전 |
